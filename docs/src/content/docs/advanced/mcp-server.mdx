As AI agents (like Claude Desktop, Cursor, and autonomous assistants) become primary consumers of APIs, exposing your backend to LLMs via the **Model Context Protocol (MCP)** is essential.

However, as emphasized by Jeremiah Lowin (creator of FastMCP) in [*Stop Converting Your REST APIs to MCP*](https://jlowin.dev/blog/stop-converting-rest-apis-to-mcp), **naive 1:1 REST-to-MCP conversions fail in production**. Exposing every HTTP endpoint as an individual tool floods the agent's context window, leaks internal endpoints, and pollutes tool arguments with transport details.

RapiDoc includes a client-side **Curated MCP Server Generator** that reads your plain OpenAPI spec, applies **smart heuristics** to drop internal and deprecated operations, strip transport headers and classify reference data, and compiles the result into an **MCP manifest**: plain JSON with one tool per operation, real JSON Schema arguments and MCP safety annotations. The manifest ships in a small TypeScript project you can run as-is.

## The Problem: The Naive 1:1 Conversion Trap

Converting every OpenAPI path directly into an MCP tool creates several critical problems for LLM agents:

<CardGrid>
  <Card title="Context Window Explosion" icon="warning">
    A typical 40-endpoint REST API exposes ~4,000 to 8,000 tokens of raw JSON schemas. This prompt overhead is re-injected on **every conversation turn**, drastically increasing inference cost and latency.
  </Card>
  <Card title="Internal & Admin Leaks" icon="error">
    Naive converters expose internal infrastructure endpoints (`/healthz`, `/metrics`, `/admin/users/debug`), confusing the model and creating potential security risks.
  </Card>
  <Card title="Auth & Transport Pollution" icon="puzzle">
    Headers like `Authorization`, `Cookie`, `X-Api-Key`, and `User-Agent` are exposed as tool arguments, forcing the model to guess or hallucinate authentication tokens.
  </Card>
</CardGrid>

## 1. Zero-Config Smart Heuristics

RapiDoc needs no extra annotations. It derives every tool and resource from standard OpenAPI fields:

1. **Tool Naming**: The tool name is the snake_case form of the `operationId` (`placeOrder` becomes `place_order`). Operations without an `operationId` get a name derived from the HTTP method and path. Duplicate names get a `_2`, `_3` suffix.
2. **Tool Descriptions**: The operation `summary` is used, else its `description`, else `METHOD /path`. HTML and Markdown are stripped and the text is truncated to 300 characters.
3. **Endpoint Exclusion**: Operations marked `x-internal: true` or `x-hidden: true`, operations marked `deprecated: true`, and webhooks are left out.
4. **Automatic Header Pruning**: Headers like `Authorization`, `Cookie`, `X-Api-Key`, `User-Agent` and other transport metadata are stripped from LLM tool arguments, as is any parameter that carries an API key named in the spec's `securitySchemes`. The runtime applies the right scheme itself, from environment variables, and reads the base URL from `servers[0]` (overridable with `API_BASE_URL`).
5. **Static Resource Classification**: A `GET` with no required parameters on a reference-data path (`/reference`, `/currencies`, `/countries`, `/tiers`, `/categories`, `/status`, `/schema`) becomes an **MCP Resource** (`reference://<name>`) instead of a tool, avoiding function-calling overhead.
6. **Safety Annotations**: Every tool carries MCP annotations: `readOnlyHint` for `GET`, `destructiveHint` for `PUT`, `PATCH` and `DELETE`, `idempotentHint` for `GET`, `PUT` and `DELETE`. Hosts use them to ask the user before running a consequential tool.
7. **Token Budget Calculation**: Real-time diagnostic calculation estimates prompt token overhead and warns when total tools exceed recommended limits (>30 tools or >5,000 tokens).

## 2. Annotated OpenAPI Example

Here is a plain OpenAPI 3.x snippet and how each operation is treated:

```yaml
openapi: 3.0.3
info:
  title: Commerce Fulfillment API
  version: 2.4.0
servers:
  - url: https://api.example.com/v2   # Base URL in the manifest
security:
  - api_key: []                         # Applied by the runtime from API_KEY

paths:
  # 1. Tool "place_order" (POST: readOnlyHint false)
  /orders:
    post:
      summary: Place a new order
      operationId: placeOrder
      parameters:
        - name: Authorization # Stripped: never a tool argument
          in: header
          schema: { type: string }
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [customerId, items]
              properties:
                customerId: { type: string }
                items: { type: array, items: { type: string } }
                shippingMethod: { type: string, enum: [standard, express, overnight] }

  # 2. Read-only tool "get_order"
  /orders/{orderId}:
    get:
      summary: Get an order
      operationId: getOrder
      parameters:
        - name: orderId
          in: path
          required: true
          schema: { type: string }

  # 3. MCP Resource "reference://currencies" (GET, no required params, reference-data path)
  /currencies:
    get:
      summary: List supported currencies
      operationId: getCurrencies

  # 4. Excluded: internal endpoint
  /admin/database/vacuum:
    post:
      summary: Trigger internal database maintenance
      x-internal: true

  # 5. Excluded: deprecated endpoint
  /orders/legacy:
    get:
      summary: Legacy order list
      deprecated: true

components:
  securitySchemes:
    api_key:
      type: apiKey
      in: header
      name: X-API-Key
```

## 3. The Manifest

The export is data, not generated code. `manifest.json` describes the whole server:

- **`server`**: `name` (snake_case of the `mcp-server-name` attribute or the API title), `version` and `description` from `info`.
- **`sources`**: one entry, named `api`, with the `baseUrl` from `servers[0]` (server variables filled with their defaults) and the spec's `securitySchemes` copied as they are.
- **`tools`**: one per operation that survives the exclusions above.
- **`resources`**: the reference-data lookups, with a `reference://` URI.
- **`workflows`**: empty for now.

Each tool has a `name`, a `description`, an `inputSchema`, MCP `annotations` and an `operation` block that tells the runtime how to make the HTTP call. The `inputSchema` is real JSON Schema: path, query, header and cookie parameters become properties by name, and the request body becomes a `body` property holding the full body schema, with nested objects, arrays, enums and `required` intact. `$ref`s are inlined, cycles are cut, and read-only properties are dropped because they never go in a request.

The `place_order` tool from the example above:

```json
{
  "name": "place_order",
  "description": "Place a new order",
  "inputSchema": {
    "type": "object",
    "properties": {
      "body": {
        "type": "object",
        "required": ["customerId", "items"],
        "properties": {
          "customerId": { "type": "string" },
          "items": { "type": "array", "items": { "type": "string" } },
          "shippingMethod": { "type": "string", "enum": ["standard", "express", "overnight"] }
        }
      }
    },
    "required": ["body"]
  },
  "annotations": { "readOnlyHint": false, "destructiveHint": false, "idempotentHint": false },
  "operation": {
    "source": "api",
    "method": "POST",
    "path": "/orders",
    "params": [{ "name": "body", "in": "body", "contentType": "application/json" }],
    "security": [{ "api_key": [] }]
  }
}
```

`operation.params` records where each argument goes (`path`, `query`, `header`, `cookie` or `body`), and `operation.security` is the operation's security requirement, else the spec's. Because the manifest holds everything a server needs, servers in other languages can read the same `manifest.json` later without regenerating anything.

## 4. The Runtime and the Exported Project

### The runtime

`runtime.js` executes any tool in the manifest with `fetch`, so the same file runs in Node, browsers and edge workers. `createMcpRuntime(manifest, { fetch, credentials, baseUrls })` returns `listTools()`, `listResources()`, `callTool(name, args)` and `readResource(uri)`. A tool call:

1. Puts each argument where `operation.params` says, percent-encoding path parameters and serializing arrays as repeated query parameters.
2. Applies the security scheme: an API key in a header, query parameter or cookie; HTTP Basic; a Bearer token for HTTP bearer, OAuth 2 and OpenID Connect.
3. Sends the request and returns an MCP result: `content` with the JSON response pretty-printed, `structuredContent` when the response is a JSON object, and `isError` with the HTTP status and body on a 4xx or 5xx.

### What is in the zip

**Export MCP Server** downloads `<server-name>-mcp.zip`:

| File | Purpose |
| :--- | :--- |
| `manifest.json` | The manifest described above |
| `runtime.js` | The runtime for operation tools; identical for every API |
| `workflow-runtime.js` | Runs workflow tools; present only when the manifest has workflows, identical for every API |
| `server.ts` | A stdio server on `@modelcontextprotocol/sdk` that registers the manifest's tools and resources and hands every call to the runtime; identical for every API |
| `package.json` | Depends on `@modelcontextprotocol/sdk`; `tsx` as a dev dependency; `npm start` runs `tsx server.ts` |
| `README.md` | How to run it and which environment variables it reads |
| `claude_desktop_config.json` | A ready-made `mcpServers` entry for Claude Desktop and Cursor |

### Running it

```bash
unzip commerce-fulfillment-api-mcp.zip -d commerce-fulfillment-api-mcp
cd commerce-fulfillment-api-mcp
npm install
API_KEY="your-key" npm start
```

### Environment variables

Credentials are read from environment variables named after the security schemes in the spec, in upper snake case: the scheme `petstore_auth` reads `PETSTORE_AUTH`, `api_key` reads `API_KEY`. `API_KEY` is also the fallback for any scheme without its own variable. HTTP Basic takes `user:password` in the scheme's variable, or `<NAME>_USERNAME` and `<NAME>_PASSWORD`. `API_BASE_URL` overrides the manifest's base URL for every source.

### Workflows as tools

When the page also has a [`<rapi-flow>`](/examples/arazzo-flow) element, the export adds one tool per Arazzo workflow. The manifest's `workflows` holds each workflow's steps with their operations resolved, and the runtime runs them: inputs become the tool's arguments, every step's parameters and body are filled from `$inputs` and earlier steps' outputs, success criteria are checked (a step without criteria succeeds on a 2xx response), `onSuccess` / `onFailure` actions (`end`, `goto`, `retry`) are followed, and the workflow's `outputs` are the result. The same runtime powers the **Run** button of `<rapi-flow>`, which runs a workflow in the browser with the credentials entered in the tied `<rapi-doc>` and lights up each step. A workflow that uses something the runtime does not run yet (a step that calls another workflow, `regex` / `jsonpath` / `xpath` criteria) is left out, and `generateMcpServer().problems` says why.

```javascript
import { buildMcpManifest, createMcpRuntime, parseArazzo } from '@rapidoc/mcp';

const arazzo = parseArazzo(readFileSync('petstore.arazzo.yaml', 'utf8'));
const manifest = buildMcpManifest(spec, { arazzo, onProblem: console.warn });
const runtime = createMcpRuntime(manifest, { credentials: { api_key: process.env.API_KEY } });
const result = await runtime.callTool('adopt_pet', { quantity: 1 }, {
  onStep: (step) => console.log(step.stepId, step.outcome, step.response?.status),
});
```

## 5. Integrating with `<rapi-doc>`

### HTML Attributes

Configure the **`mcp`** attribute on your `<rapi-doc>` element:

```html
<rapi-doc
  spec-url="/specs/my-api.yaml"
  mcp="true"
  mcp-server-name="my-api-mcp"
> </rapi-doc>
```

- **`mcp`** (`"true" | "false" | "none"`, default: `"false"`): `"true"` renders an `[Export MCP Server]` button in the API overview that downloads the project zip. `"false"`, `"none"` or an empty value hides it.
- **`mcp-server-name`** (`string`, optional): Custom identifier for the generated MCP server. Defaults to the specification title.

### Programmatic JavaScript API

You can build the manifest, trigger downloads, or inspect token costs programmatically. Every method accepts an `options` object with `serverName`, `includeInternal` and `includeDeprecated`:

```javascript
const doc = document.querySelector('rapi-doc');

// 1. Build the manifest, the project files and the token diagnostics in memory
const result = doc.generateMcpServer({ serverName: 'my_store_mcp' });
console.log(result.manifest.tools.map((t) => t.name)); // ['place_order', 'get_order', ...]
console.log(result.files['server.ts']);                 // every file of the zip, path → text
console.log(result.budget);                             // { totalTools: 5, estimatedTokens: 850, ... }
console.log(result.hostConfig);                         // Claude Desktop / Cursor config JSON

// 2. Download the project as <server-name>-mcp.zip
doc.downloadMcpServer();

// 3. Inspect token budget overhead before exporting
const budget = doc.getMcpBudget();
console.log(`Overhead: ~${budget.estimatedTokens} tokens/turn across ${budget.totalTools} tools.`);
```

`result.files` has the keys `manifest.json`, `server.ts`, `runtime.js`, `package.json`, `README.md` and `claude_desktop_config.json`. `getMcpBudget()` returns `{ totalTools, totalResources, estimatedTokens, consequentialCount, warnings }`, where `consequentialCount` is the number of tools that are not read-only.

### From the command line

`npx rapidoc mcp export openapi.yaml` writes the same project as the Export button, and `npx rapidoc mcp serve openapi.yaml` runs the server over stdio without writing files ([Command-Line Tools](/docs/advanced/command-line/#turn-it-into-an-mcp-server)).

### In Node: `@rapidoc/mcp`

The same builder, runtime and project writer are available without the browser or any element, for build scripts and servers:

```bash
npm install @rapidoc/mcp
```

```javascript
import { readFileSync } from 'node:fs';
import { parse } from 'yaml';
import { buildMcpManifest, createMcpRuntime, writeMcpProject } from '@rapidoc/mcp';

const spec = parse(readFileSync('openapi.yaml', 'utf8'));
const manifest = buildMcpManifest(spec, { serverName: 'petstore' });

// Call a tool directly, with credentials by security scheme
const runtime = createMcpRuntime(manifest, { credentials: { api_key: process.env.API_KEY } });
const result = await runtime.callTool('get_pet_by_id', { petId: 1 });

// Or write the same project the Export button downloads
const files = writeMcpProject(manifest); // path → text
```

`@rapidoc/mcp` ships TypeScript types (`McpManifest`, `McpRuntime`, ...). Its only dependency is `yaml` (for Arazzo documents); requests use Node's `fetch`.
