RapiDoc includes a built-in authentication console that lets developers authenticate against any OAuth 2.0 Identity Provider (IdP), obtain access tokens, and execute authenticated API calls directly from documentation pages.

<Aside type="tip" title="Interactive Demo">

</Aside>

## The Short Version (TL;DR)

Setting up OAuth 2.0 in RapiDoc requires only three straightforward steps:

1. **Register your client** with your Authorization Server (Okta, Auth0, Azure AD, Keycloak, etc.) and register your redirect URI (`https://your-domain.com/oauth-receiver.html`).
2. **Create `index.html`** containing the `<rapi-doc>` element pointing to your OpenAPI specification.
3. **Create `oauth-receiver.html`** in the same directory containing the `<oauth-receiver>` element.

That is all it takes! RapiDoc handles the popup window lifecycle, token exchange, and automatic `Authorization: Bearer <token>` header injection.

## Architecture & Complete Flow

When a developer clicks **"Authorize"** in RapiDoc, the Authorization Code flow executes across two browser windows and your Identity Provider:

<OAuthFlowDiagram />

### Detailed Step-by-Step Breakdown

1. **Initiate Authentication**: The user clicks **"Authorize"** on an endpoint or the top security bar. `<rapi-doc>` opens a lightweight browser popup window pointing to `oauth-receiver.html`.
2. **Redirect to IdP**: `<oauth-receiver>` immediately constructs the authorization URL with your `client_id`, requested `scopes`, `redirect_uri`, and PKCE code challenge, redirecting the user to the IdP's `/authorize` screen.
3. **User Consent & Code Issuance**: The user signs in and approves scopes. The IdP redirects the popup back to `oauth-receiver.html?code=<AUTH_CODE>&state=<STATE>`.
4. **Local Parameter Relay**: The native `<oauth-receiver>` custom element extracts the authorization code from the URL, relays it to `<rapi-doc>` in the parent window via `window.postMessage()`, and automatically closes the popup window.
5. **Token Exchange**: `<rapi-doc>` sends a POST request to your IdP's `/token` endpoint containing the authorization code, client ID, and PKCE `code_verifier` (or client secret).
6. **Token Persistence**: The IdP returns the access token. RapiDoc securely saves the token in memory and automatically attaches `Authorization: Bearer <token>` to all subsequent interactive **TRY** requests.

## The Two Required Files

You only need to serve two static HTML files from your web server:

### 1. `index.html` (Primary Documentation)

Embed the `<rapi-doc>` custom element pointing to your OpenAPI spec. If `oauth-receiver.html` is hosted in the same directory, no additional URL configuration is needed:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <title>API Documentation</title>
    <script type="module" src="https://unpkg.com/rapidoc/dist/rapidoc-min.js"></script>
  </head>
  <body>
    <rapi-doc spec-url="https://mrin9.github.io/RapiDoc/specs/oauth.yaml"></rapi-doc>
  </body>
</html>
```

<Aside type="note" title="Custom Receiver Path">
  If your receiver page is located at a different path or sub-folder, pass the `oauth-receiver` attribute to `<rapi-doc>`:
  ```html
  <rapi-doc
    spec-url="/openapi.json"
    oauth-receiver="/auth/oauth-receiver.html"
  ></rapi-doc>
  ```
</Aside>

### 2. `oauth-receiver.html` (Authentication Callback)

This file must be named `oauth-receiver.html` and placed alongside `index.html`. It contains RapiDoc's companion `<oauth-receiver>` custom element:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <title>OAuth Receiver</title>
    <script type="module" src="https://unpkg.com/rapidoc/dist/rapidoc-min.js"></script>
  </head>
  <body>
    <oauth-receiver></oauth-receiver>
  </body>
</html>
```

<Aside type="tip" title="Zero Boilerplate Scripting">
  You do not need to write URL query parsers or `window.postMessage` listeners. The `<oauth-receiver>` element is bundled inside `rapidoc-min.js` and automatically:
  - Parses query parameters (`?code=...`) for the **Authorization Code** flow.
  - Parses hash fragments (`#access_token=...`) for the **Implicit** flow.
  - Dispatches message events to `window.opener` with an automatic fallback to `sessionStorage`.
  - Cleans up and closes the popup window once transmission succeeds.
</Aside>

## OpenAPI Specification Configuration

Declare standard OpenAPI 3.0 or 3.1 OAuth 2.0 security schemes under `components.securitySchemes`.

### Standard Security Scheme

```yaml
openapi: 3.0.3
info:
  title: Protected API Service
  version: 1.0.0
servers:
  - url: https://api.example.com/v1

paths:
  /user/profile:
    get:
      summary: Retrieve current user profile
      security:
        - OAuthScheme:
            - read:profile
            - email
      responses:
        '200':
          description: Successful response

components:
  securitySchemes:
    OAuthScheme:
      type: oauth2
      description: Enterprise OAuth 2.0 with Authorization Code flow
      flows:
        authorizationCode:
          authorizationUrl: https://auth.example.com/oauth2/v1/authorize
          tokenUrl: https://auth.example.com/oauth2/v1/token
          scopes:
            read:profile: Grants read access to user profile information
            write:profile: Grants write access to user profile settings
            email: Grants access to the user's primary email address
```

## Vendor Extensions for Seamless Onboarding

RapiDoc provides custom OpenAPI vendor extensions to streamline the developer experience during testing and sandboxing. You can define these extensions at the scheme level or under individual flows:

| Extension | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `x-client-id` | `string` | — | Pre-populates the Client ID field in the authorization modal. |
| `x-client-secret` | `string` | — | Pre-populates the Client Secret field *(intended for testing/sandbox environments only)*. |
| `x-default-scopes` | `string` or `array` | — | Pre-selects default scopes in the permissions checklist. |
| `x-pkce-only` | `boolean` | `false` | When set to `true`, enforces PKCE and hides the client secret field entirely from the UI. |
| `x-receive-token-in` | `string` | `request-body` | Specifies whether client credentials are sent in the `request-body` (`client_secret_post`) or `header` (`client_secret_basic`). |
| `x-receive-token-in-options` | `array` | `["request-body", "header"]` | Restricts the client authentication options available in the UI dropdown. |

### Complete Specification Example

```yaml
components:
  securitySchemes:
    # 1. Public Client Flow (PKCE Enforced)
    public-oauth:
      type: oauth2
      description: Public client authorization flow with PKCE
      flows:
        authorizationCode:
          authorizationUrl: https://demo.duendesoftware.com/connect/authorize
          tokenUrl: https://demo.identityserver.io/connect/token
          scopes:
            openid: OpenID Connect identity
            profile: User profile information
            email: User email address

          # Pre-fill Client ID and default scopes
          x-client-id: interactive.public
          x-default-scopes:
            - openid
            - profile

          # Enforce PKCE: removes Client Secret input from UI
          x-pkce-only: true

    # 2. Confidential / Sandbox Client Flow
    confidential-sandbox:
      type: oauth2
      description: Sandbox test scheme with pre-filled test credentials
      
      # Applies to all flows defined within this scheme
      x-client-id: interactive.confidential.short
      x-client-secret: demo-secret-key-12345
      x-default-scopes: openid email
      x-receive-token-in: request-body # Default: request-body ('request-body' | 'header')
      
      flows:
        authorizationCode:
          authorizationUrl: https://demo.duendesoftware.com/connect/authorize
          tokenUrl: https://demo.identityserver.io/connect/token
          scopes:
            openid: OpenID Connect identity
            email: User email address
```

## Troubleshooting & Best Practices

<Aside type="caution" title="Common Configuration Gotchas">
  - **Redirect URI Mismatch**: Ensure the redirect URI registered in your IdP console exactly matches the URL where `oauth-receiver.html` is served (including protocol and port, e.g. `http://localhost:4321/oauth-receiver.html`).
  - **CORS on Token Endpoint**: The authorization server's `/token` endpoint must return standard CORS headers (`Access-Control-Allow-Origin: *` or your documentation origin) because `<rapi-doc>` performs a browser-side `fetch` POST request to exchange the code for a token.
  - **Client Authentication (Header vs Request Body)**: By default, RapiDoc sends client credentials in the POST `request-body` (`client_secret_post`) to minimize browser CORS preflight friction. If your authorization server strictly requires HTTP Basic authentication (`client_secret_basic`), set `x-receive-token-in: header` or switch the dropdown in the UI.
  - **Production Security**: Never commit production client secrets into public OpenAPI specifications. Use `x-pkce-only: true` for public documentation and reserve `x-client-secret` strictly for mock or sandbox instances.
</Aside>
