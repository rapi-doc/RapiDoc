An API reference shows operations one at a time. Integrators also need the order: find a pet, check it, order it, read the order back. [Arazzo](https://spec.openapis.org/arazzo/latest.html) describes those sequences, and `<rapi-flow>` draws them: one box per step, linked to its operation, the values each step passes on, and the success and failure branches. Readers can run a workflow from the page and watch each step answer.

<Aside type="tip" title="See it running">
  The [Arazzo Workflows guide](/guides/workflows) runs a workflow against the in-browser mock, the [rapi-flow example](/examples/arazzo) puts the diagram next to a full API reference, and the [multi-API example](/examples/arazzo-multi) pairs it with one `<rapi-doc-mini>` per API.
</Aside>

## Load it

`<rapi-flow>` is a separate bundle, so pages that only use `<rapi-doc>` don't download it.

```html
<script type="module" src="https://unpkg.com/rapidoc/dist/rapidoc-min.js"></script>
<script type="module" src="https://unpkg.com/rapidoc/dist/rapidoc-flow-min.js"></script>

<rapi-flow arazzo-url="/specs/petstore.arazzo.yaml" for="thedoc"></rapi-flow>
<rapi-doc id="thedoc" spec-url="/specs/petstore.yaml"></rapi-doc>
```

With a bundler, `import 'rapidoc/flow';` registers the element. It carries its own copy of Lit and the Arazzo runtime; `rapidoc-min.js` carries no Arazzo code.

## Standalone or paired

- **Paired** (`for="<id>"`): the element uses that `<rapi-doc>`'s spec, its selected server and the credentials entered in its Authentication section. Clicking a step scrolls the reference to the step's operation. If the `<rapi-doc>` has `mock-server="true"`, runs go to the in-browser mock. A workflow that calls several APIs can be paired with one element per API (see [one element per API](#one-element-per-api)).
- **Standalone**: the element loads each OpenAPI source of the Arazzo file itself (`spec-url` replaces the first one's URL) and shows its own credentials fields, one per security scheme of the loaded specs. Values typed there stay in the page. A paired element's sources get no fields: it has its own.

## API sources

An Arazzo document names the APIs its steps call in `sourceDescriptions`. `<rapi-flow>` lists them in the card above the diagram, under the Arazzo document's URL (or the box that loads one): **API sources**, with each one's name and URL (and its type when it is not `openapi`, such as another Arazzo document). The diagram's first box then holds the workflow's **Inputs** alone. A diagram drawn without the element (the portal's `{% workflow %}` tag, `renderArazzoWorkflow`) lists them at the top of its first box instead, unless `showSources: false` is passed.

A document can name several sources (Rapid Parcels' `ship-a-parcel` uses `rates`, `shipments` and `tracking`). Then:

- **Loading**: `<rapi-flow>` fetches every `openapi` source, its URL taken relative to the Arazzo file. `arazzo` sources (other Arazzo documents) are listed but not loaded. A source that fails to load is listed under the diagram, and the steps on it show their `operationId` with "(not found)".
- **Finding a step's operation**: an `operationId` is looked up in the sources in order, and the first that has it wins. When two APIs share an id, qualify it: `$sourceDescriptions.shipments.createShipment`. An `operationPath` (`{$sourceDescriptions.<name>.url}#/paths/...`) names its source.
- **A single paired `<rapi-doc>`** shows one API: the **first** source (or the one whose spec it shows). `<rapi-flow>` takes that source from it (its processed spec, its selected server, its credentials) and loads the others itself. Clicking a step on another source does not scroll the reference, which does not have that operation. To show every API, pair one element per source (next section).
- **Runs**: each source's requests go to the server selected in its paired element, else the first server of its own spec; `server-url` replaces the first source's. Credentials apply by security scheme id, across sources. An element's in-browser mock answers the steps on its own source; steps on a source with no paired element, or whose element does not mock, go to their servers. With `server-is-mock="true"`, those requests carry `Prefer: code=`, so a mock server that serves all the APIs (`rapidoc mock` serves a portal's APIs side by side) answers them.
- **MCP export**: one manifest source per loaded API; a workflow tool's steps call each one at its own server.

## One element per API

`for` takes several ids separated by spaces, one element per OpenAPI source. Each element supplies its source's spec, server, credentials and mock, and clicking a step shows its operation in the element of its source. `<rapi-doc-mini>` suits this best: `<rapi-flow>` sets its `filter-operations` to the shown workflow's operations of its API, in step order, and updates it when the reader picks another workflow, so each mini lists just the calls the workflow makes.

```html
<rapi-flow arazzo-url="/workflows/ship-a-parcel.arazzo.yaml" allow-arazzo-url-load="true"
           for="rates-api shipments-api tracking-api"></rapi-flow>

<rapi-doc-mini id="rates-api" arazzo-source="rates" mock-server="true"></rapi-doc-mini>
<rapi-doc-mini id="shipments-api" arazzo-source="shipments" mock-server="true"></rapi-doc-mini>
<rapi-doc-mini id="tracking-api" arazzo-source="tracking" mock-server="true"></rapi-doc-mini>
```

- **Which element goes with which source**: the source its `arazzo-source` attribute names; else the source whose URL it has loaded (`spec-url`, resolved against the page, equal to the source URL resolved against the Arazzo file); else the next source not taken, in document order. An element named for a source the document does not have is left alone, so a page can list elements for several Arazzo files in one `for`.
- **Loading**: with `allow-arazzo-url-load="true"`, `<rapi-flow>` loads each source into its element, so the elements need no `spec-url`: a `<rapi-doc>` loads it at once, a mini once its filter is set, so it is fetched filtered from the start. `<rapi-flow>` loads a mini's source itself too, to resolve every workflow's steps; a `<rapi-doc>`'s source is fetched only by the `<rapi-doc>`. Without the box, give each element its `spec-url`.
- **Changing `for`**: `<rapi-flow>` pairs the elements again without loading the Arazzo file again. Elements are paired after `flow-loaded` fires, so a `flow-loaded` listener can create the elements for the document's sources and set `for`. The [multi-API example](/examples/arazzo-multi) writes its three minis in the page instead, each with `arazzo-source` and `spec-url`, for Rapid Parcels' `ship-a-parcel`.

## Links to a step

With `update-route="true"`, picking a workflow or clicking a step puts them in the address as query parameters:

```text
/docs/shipping?workflow=shipParcel&step=label
```

Opening that link shows the `shipParcel` workflow, selects `label`, scrolls its box into view and shows its operation in the paired element, once that element has loaded its spec. Unknown ids are ignored.

- **Query parameters, not the hash**: `<rapi-doc>` keeps the hash (`#get-/pets`) for its operations and rewrites it as the reader scrolls, so the two never overwrite each other. A link can carry both: `?workflow=shipParcel&step=label#get-/shipments/{shipmentId}/label`.
- **No history entries**: the address is replaced, as `<rapi-doc>` does, so Back leaves the page instead of stepping through clicks.
- **Routers**: `history.state` is kept, so a single-page app's router (Vue Router, React Router) keeps its data. In a router's history mode both elements work as on a plain page. A hash-mode router owns the hash: set `update-route="false"` on `<rapi-doc>` there; `<rapi-flow>`'s parameters still work.
- **One element per page**: the parameter names are fixed, so set it on one `<rapi-flow>` only.
- A document loaded from the URL box drops the old step and shows its first workflow.

## Attributes

| Attribute | Default | Meaning |
| :--- | :--- | :--- |
| `arazzo-url` | | URL of the Arazzo 1.x document, YAML or JSON. |
| `spec-url` | | Replaces the URL of the first OpenAPI source description. Other sources are fetched relative to the Arazzo file. |
| `workflow-id` | first workflow | The workflow to show. With several workflows, a picker in the header switches between them. |
| `for` | | `id` of a `<rapi-doc>` or `<rapi-doc-mini>` on the page to take the spec, server, credentials and mock from, or several ids separated by spaces, one per OpenAPI source (see [one element per API](#one-element-per-api)). |
| `view` | `expanded` | `expanded` shows each step's inputs and actions in its box; `compact` shows the operation, the values that come from the workflow's inputs or earlier steps (constants are counted in one line), and the gotos and retries whose lines leave the box, each line starting at its action. |
| `show-view-toggle` | `true` | `false` hides the Compact / Expanded switch. |
| `allow-arazzo-url-load` | `false` | `true` shows a box above the diagram to load any Arazzo document by URL (the server must allow cross-origin requests). With `for`, the paired elements follow the document: whenever it changes (from the box or `arazzo-url`), each one loads its OpenAPI source, unless it already shows that spec. A URL that fails to load leaves the current document and the elements as they were, with the error under the box. Without the box, the document's URL shows as text (part `url`). Either way it sits in a card above the diagram, with the document's API sources below it. |
| `update-route` | `false` | `true` keeps the shown workflow and the selected step in the page's address, `?workflow=<id>&step=<id>`, so a link opens that workflow with that step selected, scrolled into view and its operation shown in the paired element (see [Links to a step](#links-to-a-step)). |
| `allow-run` | `true` | `false` hides the run panel: the diagram only. |
| `server-url` | | Base URL the first OpenAPI source's requests go to in runs, instead of the server its paired element selected or the spec's first server. |
| `mcp` | `false` | `true` shows an **Export MCP Server** button: an MCP server with one tool per workflow of the document (each one the runtime can run) and none per operation, calling every API source. |
| `mcp-server-name` | | The exported server's name; defaults to the Arazzo document's title. |
| `server-is-mock` | `false` | `true` says that server is a mock that picks its response status from a `Prefer: code=` header (`rapidoc mock`, Prism): the run panel shows **Mock Response Status** and the button reads "Run workflow (Mock)". Not needed when the paired elements have `mock-server="true"`. |
| `theme` | `ember` | One of RapiDoc's theme presets, or a custom accent; same values as on `<rapi-doc>`. |
| `color-scheme` | `dark` | `dark`, `light`, `system`, or `auto` (follows the page's `data-theme`). |

## Events

All events bubble and cross the shadow boundary (`composed`).

| Event | `detail` | When |
| :--- | :--- | :--- |
| `flow-loaded` | `{ doc, problems }` | The Arazzo document and its sources are loaded. `problems` lists validation findings. |
| `step-click` | `{ workflowId, stepId, operation, workflowRef }` | A step box is clicked or activated with the keyboard. |
| `view-change` | `{ view }` | The reader switched between compact and expanded. |
| `workflow-run` | `{ workflowId, inputs, result, trace }` | A run finished. `result` is the MCP tool result; `trace` has one entry per step attempt with its request and response. |

The element also exposes `arazzoDocument` (the parsed document), `workflowRuntimeSource`, which a paired `<rapi-doc>` uses to add workflow tools to its [MCP export](/docs/ai/mcp-server/#workflows-as-tools), and the `statusCodes` property that fills the Mock Response Status table (see below).

## Running a workflow

The run panel under the diagram has the workflow's inputs (filled with their defaults), the credentials fields when the element is standalone, and **Run workflow**. While it runs, the step whose request is in flight is highlighted; each finished step adds an entry to the log with its HTTP status, which opens to see the request and response. The workflow's outputs appear as a table at the end.

Runs call the API from the reader's browser, as **Try** does, so a real API must allow cross-origin requests from the docs site.

## Running against a mock

A workflow is easiest to show and test before the API exists, or without touching real data.

### The in-browser mock

Turn on [`mock-server`](/docs/mocking/in-browser/) on the paired elements. Every request of the run to their APIs is answered in the page from the spec's examples and schemas; the log's heading reads "Log (mocked responses)" when every response was mocked; when only some were (a source with no mocking element), those entries say "mocked". The mock answers 200 unless told otherwise: for APIs that answer 201 or 204, set `mock-server-status-code=""` on the element, so each operation gets its first 2xx response and the workflow's `$statusCode == 201` checks pass.

```html
<rapi-flow arazzo-url="/specs/petstore.arazzo.yaml" for="thedoc"></rapi-flow>
<rapi-doc id="thedoc" spec-url="/specs/petstore.yaml" mock-server="true"></rapi-doc>
```

The run panel then has a **Mock Response Status** table: the status codes the mock answers with during that run, one row per step and a default row for every other step.

- Empty: the element's own setting (`mock-server-status-code`: 200 by default, the operation's first 2xx response when it is empty).
- One code in the default row, such as `404`: every request of the run gets it. In the sample `adoptPet` workflow, a 404 on the first step takes its `onFailure` branch and ends the run.
- A code on one step, such as `503, 200` on `placeOrder`: that step's first attempt gets 503 and its retry gets 200, while the other steps succeed. With several codes, a step takes the next code on each attempt (**in turn**) or one at random.

The table sets each paired element's mock for that run only, per operation of its API, and puts the previous setting back afterwards. Pages can fill it from a script through the `statusCodes` property: `flow.statusCodes = { "*": "200", placeOrder: "503, 200" }`.

### A mock server

To run against a mock that behaves more like the real API (request validation, generated data, OAuth scope checks), start [`rapidoc mock`](/docs/mocking/mock-server/) and point the run at it:

```html
<rapi-flow arazzo-url="/specs/petstore.arazzo.yaml" spec-url="/specs/petstore.yaml"
           server-url="http://localhost:4010/petstore" server-is-mock="true"></rapi-flow>
```

Or list the mock as a server in the spec and pick it in the paired element's server list. With OAuth, sign in through **Authorize** in `<rapi-doc>`, or paste a token into the standalone credentials field; the mock checks it like the real API would.

With `server-is-mock="true"`, the same **Mock Response Status** table works here: each step's codes are sent as `Prefer: code=<status>`, which `rapidoc mock` honors. Without it, and with no paired element mocking, the table is not shown, since a real API ignores the header.

## What runs

| Arazzo feature | Runs |
| :--- | :--- |
| `inputs`, `outputs`, step `outputs` | Yes |
| `$inputs`, `$steps.<id>.outputs`, `$response.body#/pointer`, `$response.header`, `$statusCode` | Yes |
| `successCriteria` with simple conditions (`==`, `!=`, `<`, `>`, `&&`, `||`) | Yes |
| `onSuccess` / `onFailure`: `end`, `goto`, `retry` with `retryAfter` and `retryLimit` | Yes |
| `requestBody` with payload and replacements | Yes |
| `regex`, `jsonpath` and `xpath` criteria | Not yet |
| [`x-security`](#credentials-in-the-workflow-x-security) on a workflow or step: API key, HTTP Basic, bearer | Yes |
| `x-security` with HTTP Digest | No |
| `x-allowReserved` on a step's query parameter, and the OpenAPI parameter's `allowReserved` | Yes |
| [`x-operation`](#calls-outside-the-api-sources-x-operation): a step that calls a URL outside the sources | Yes |
| Steps that call another workflow, AsyncAPI sources | Not yet |

A step without `successCriteria` succeeds on a 2xx status; the first matching action runs; a run stops after 1,000 steps. A workflow that uses something not supported yet is still drawn, with a note that explains why it can't run.

## Credentials in the workflow (`x-security`)

`<rapi-flow>` supports the `x-security` extension of [Redocly Respect](https://redocly.com/docs/respect/extensions/x-security), so an Arazzo file can say which credentials each request sends instead of relying on what the reader typed into the Authentication section. Put it on a step, or on the workflow for every step:

```yaml
workflows:
  - workflowId: adoptPet
    inputs:
      type: object
      properties:
        apiKey: { type: string, format: password }
        token: { type: string, format: password }
    x-security:                      # every step
      - scheme: { type: http, scheme: bearer }
        values: { token: $inputs.token }
    steps:
      - stepId: checkPet
        operationId: getPetById
        x-security:                  # this step only
          - schemeName: api_key      # a scheme of the step's OpenAPI source
            values: { apiKey: $inputs.apiKey }
```

- Each entry has either `schemeName` (a scheme in the step's source's `components.securitySchemes`) or an inline `scheme`, plus `values`: `apiKey` for an API key (`in: header`, `query` or `cookie`), `username` and `password` for HTTP Basic, `token` for HTTP Bearer, OAuth 2 and OpenID Connect.
- Values are usually `$inputs.<name>`, or `$steps.<id>.outputs.<name>` for a token an earlier step returned. An input that is not given sends nothing for that entry.
- The workflow's entries are sent first, then the step's, after the credentials entered in the page. Where two set the same header, query parameter or cookie, the later one wins, so the step's override the workflow's.
- Inputs with `format: password` get a password field in the run panel, and the log shows them as `••••••`. The diagram lists each step's credentials under **Security** with the scheme, and never shows a value written into the file itself.
- HTTP Digest is not supported: a browser cannot read the API's challenge across origins. A workflow that uses it is drawn, with a note that it cannot run.

In an [MCP export](/docs/ai/mcp-server/#workflows-as-tools), password inputs are arguments of the workflow's tool, so the agent supplies them. To keep a secret away from the agent, leave it out of `x-security` and set the scheme's environment variable instead.

## Calls outside the API sources (`x-operation`)

A step can call an endpoint that no source description describes, such as a file download link an earlier step returned, or a third-party API, with the `x-operation` extension of [Redocly Respect](https://redocly.com/docs/respect/extensions/x-operation). It takes the place of `operationId`:

```yaml
steps:
  - stepId: upload
    operationId: uploadFile
    outputs:
      fileUrl: $response.body#/url
  - stepId: download
    x-operation:
      url: $steps.upload.outputs.fileUrl   # or an absolute URL: https://cdn.example.com/files/{id}
      method: get
    successCriteria:
      - condition: $statusCode == 200
```

- `url` is an absolute `http` or `https` URL, or a runtime expression; `{$inputs.x}` can be interpolated into a URL too. `method` is any HTTP method, in any case.
- `parameters` work as for other steps: query, header and cookie values are added, and a path parameter fills its `{name}` in the URL. `requestBody`, `successCriteria`, actions and `outputs` are the same.
- No source credentials are sent, since the URL belongs to no source. To send some, add [`x-security`](#credentials-in-the-workflow-x-security) with an inline `scheme` (`schemeName` has no source to look in).
- The diagram draws the step with a dashed border, its method and URL, and an **external** tag. A URL computed from an earlier step lists that step under **URL**, like any value passed between steps. The step does not open anything in the reference.
- Runs call the URL from the reader's browser, so that server must allow cross-origin requests from the docs site; the log says so when the request fails. A mock does not answer these steps.

In an [MCP export](/docs/ai/mcp-server/#workflows-as-tools), the server makes the request. A URL written into the Arazzo file is always called; a URL computed at run time (from an input or a response) is called only on a host the workflow names (its API sources' servers, or another step's written-out URL), so an agent or an API can't send the server to an address of its choosing. List more hosts in `EXTERNAL_HOSTS` (comma-separated, `*` for any), which the exported server, `rapidoc mcp serve` and `rapidoc serve` all read, or with the runtime's `externalHosts` option.

## Reserved characters in query values (`x-allowReserved`)

Query values are percent-encoded, so `https://a.example/x` is sent as `https%3A%2F%2Fa.example%2Fx`. When the API expects the value as is (a URL, a filter expression), set `x-allowReserved: true` on the step's parameter, the Arazzo counterpart of OpenAPI's `allowReserved`, as in [Redocly Respect](https://redocly.com/docs/respect/extensions/x-allow-reserved):

```yaml
parameters:
  - name: filter
    in: query
    value: https://example.com/path/to;x,y
    x-allowReserved: true        # ?filter=https://example.com/path/to;x,y
```

The reserved characters `: / ? [ ] @ ! $ & ' ( ) * + , ; =` are then sent unencoded; spaces and other characters are still encoded, and so is `#`, which would end the URL's query. A query parameter with `allowReserved: true` in the OpenAPI document is sent the same way without the extension; `x-allowReserved: false` turns that off for one step.

## Slots

Put your own markup at the top or bottom of the element with `slot="header"` or `slot="footer"`: a logo, a title, a server switch, links. It stays in the page's DOM, so the page's CSS styles it and its scripts find it, and it scrolls with the diagram. Its spacing is yours: the element adds none around it.

```html
<rapi-flow arazzo-url="/workflows/ship-a-parcel.arazzo.yaml" for="thedoc">
  <div slot="header">
    <img src="/logo.svg" alt="Rapid Parcels" height="28">
  </div>
  <p slot="footer">Questions? <a href="/support">Contact support</a>.</p>
</rapi-flow>
```

| Slot | Where |
| :--- | :--- |
| `header` | At the top, above the card with the Arazzo document's URL and API sources. |
| `footer` | At the bottom, below the run panel. |

The [rapi-flow example](/examples/arazzo) puts the `<rapi-flow>` logo and its Real / Mock server switch in the header slot; the [multi-API example](/examples/arazzo-multi), the Rapid Parcels logo.

## Styling

`theme` and `color-scheme` work as on `<rapi-doc>`, and the element reads the same [CSS custom properties](/docs/theming/overview). Its CSS parts: `mcp-export`, `document` (the card with the URL and the API sources), `sources`, `url`, `url-form`, `url-input`, `url-load`, `url-error`, `header`, `title`, `select`, `description`, `view-toggle`, `diagram`, `run`, `run-inputs`, `run-button`, `run-stop`, `message`, `problems`.

```css
rapi-flow::part(diagram) {
  max-height: 32rem;
}
```

## In a developer portal

`@rapidoc/portal` draws workflows in docs pages with the `{% workflow file="…" id="…" %}` Markdoc tag: the diagram is rendered as static SVG at build time, and `rapidoc-flow-min.js` loads only when a reader clicks **Run workflow**. The portal build also turns each workflow into an MCP tool for `rapidoc serve`'s `/mcp` endpoint.
