# Demo scenario and permission model

Status: **decided** (S1–S6 accepted 2026-10-27). Step 2 is done: the specs, docs and config live in `demo-api-portal` (Auth0 checklist: `demo-api-portal/auth0-setup.md`). It drives the sample specs (step 2), the Auth0 setup (step 4), the portal access rules (step 5) and the end-to-end test matrix (step 6). Change names here first; everything else copies them.

## 1. The company

**Rapid Parcels** (fictional): a parcel network that lets online shops ship parcels, lets anyone track them, works with partner carriers for the last mile, and runs billing and administration internally.

The domain is close to the old Cosmo Cargo demo on purpose, so the Auth0 users you already created (ship@, track@, review@, manager@) keep their meaning. The brand, specs and docs are new.

### Domains

| Use | Domain | Why |
| :--- | :--- | :--- |
| The fictional company in specs and docs (hosts, sample emails such as `jane.doe@rapidparcels.example`) | `rapidparcels.example` | Reserved: never resolves or receives mail, and can't belong to a real company |
| Test users' emails | `@rapidocui.com` | Real inboxes (Resend receives for the domain), needed for Auth0 verification and password-reset mail |
| Auth0 tenant | `rapidocui.us.auth0.com` | Later perhaps a custom login domain (`login.rapidocui.com`) |
| Auth0 API identifier (token audience) | `https://api.rapidocui.com` | A name only (Auth0 never calls it); on a domain we own so it stays unique |
| Where the demo runs | `localhost` now; if hosted later, e.g. `demo.rapidocui.com` (portal) and `mock.rapidocui.com` (mock) | Must resolve, so on a domain we own |

Sample payloads never use `rapidocui.com` addresses: that domain really receives mail.

## 2. APIs

Six APIs, each built to exercise something specific. `id` is the portal id (`/apis/<id>`) and the mock path (`http://localhost:4010/<id>`).

| id | API | Audience | Auth in the spec | What it is there to test |
| :--- | :--- | :--- | :--- | :--- |
| `rates` | Rates API | Everyone | None | A fully public API; examples on every operation; OpenAPI 3.1 |
| `shipments` | Shipments API | Shop developers | OAuth2 (`shipments:read`, `shipments:write`) | Create, list, cancel; pagination; several error responses per operation (`Prefer: code=`); 3.1 `webhooks` (`shipment.status_changed`) |
| `tracking` | Tracking API | Tracking integrators | OAuth2 (`tracking:read`) + API key | OpenAPI **3.0** with `callbacks` (event subscriptions); two security schemes on one operation |
| `carriers` | Carrier Partners API | Partner carriers | OAuth2 (`carriers:read`, `carriers:write`) | Multipart file upload (labels); `oneOf` + `discriminator` (pickups, service types). One file for now: split specs can't load in a portal until relative-`$ref` files are published (known gap); the Cosmo Cargo fixture's `label-v3.json` covers that case meanwhile |
| `billing` | Billing API | Internal finance | OAuth2 (`billing:read`, `billing:write`) | Schema-only operations (no examples, so the mock must generate data); money and date formats; idempotency header |
| `admin` | Admin API | Platform admins | OAuth2 (`admin:read`, `admin:write`) | **Large spec** (144 operations, generated by `scripts/generate-admin-spec.mjs`) for performance and search; deep nesting; deprecated operations |

Every protected operation lists its `oauth2` scope and, as an alternative, `bearerAuth` for a pasted token. The **oauth2 scope is the permission the operation needs, whichever scheme carries the token** (the mock enforces it for bearer tokens too). Tracking also accepts `apiKey` (`X-Api-Key`).

Every spec lists two servers: the mock (`http://localhost:4010/<id>`) first, then `https://api.rapidparcels.example/v1` (documentation only, does not exist). If the mock is hosted later, `https://mock.rapidocui.com/<id>` joins the list.

## 4. People, roles and permissions

Two different things travel in a sign-in, and they stay separate:

- **Roles** (Auth0 roles → the portal's `groups`, claim `https://rapidoc/roles`): what you may **read** in the portal.
- **Permissions** (Auth0 API permissions → the access token's `permissions` claim, Auth0 API `https://api.rapidocui.com`): what you may **execute** against the APIs (the mock checks them).

| User | Persona | Role | API permissions |
| :--- | :--- | :--- | :--- |
| *(not signed in)* | Visitor | — | — |
| `ship@rapidocui.com` | Shop developer | `shipper` | `shipments:read`, `shipments:write` |
| `track@rapidocui.com` | Tracking integrator | `tracker` | `tracking:read` |
| `review@rapidocui.com` | Technical reviewer | `reviewer` | *none* |
| `partner@rapidocui.com` *(new)* | Carrier engineer | `carrier-partner` | `carriers:read`, `carriers:write` |
| `finance@rapidocui.com` *(new)* | Finance analyst | `finance` | `billing:read`, `billing:write` |
| `manager@rapidocui.com` | Platform admin | `platform-admin` | all permissions |

Naming: roles are kebab-case nouns; permissions are `<api id>:<read|write>`, so a spec's scopes, Auth0's permissions and the mock's checks use the same strings.

| | Visitor | shipper | tracker | reviewer | carrier-partner | finance | platform-admin |

| Shipments API, `/docs/shipping/**` | 🔒 | ✅ | — | ✅ | — | — | ✅ |
| Tracking API | 🔒 | — | ✅ | ✅ | — | — | ✅ |
| Carriers API, `/docs/partners/**` | 🔒 | — | — | ✅ | ✅ | — | ✅ |
| Billing API, `/docs/internal/**` | 🔒 | — | — | — | — | ✅ | ✅ |
| Admin API | 🔒 | — | — | — | — | — | ✅ |

🔒 = sent to sign-in · — = "access denied" page · locked links show a lock icon.

As config (step 5 copies this into the demo):

```yaml
access:
  default: public
  rules:
    - path: /apis # redirect to the catalog
      allow: public
    - path: /apis/rates/**
      allow: public
    - path: /apis/shipments/**
      allow: { groups: [shipper, reviewer, platform-admin] }
    - path: /docs/shipping/**
      allow: { groups: [shipper, reviewer, platform-admin] }
    - path: /apis/tracking/**
      allow: { groups: [tracker, reviewer, platform-admin] }
    - path: /apis/carriers/**
      allow: { groups: [carrier-partner, reviewer, platform-admin] }
    - path: /docs/partners/**
      allow: { groups: [carrier-partner, reviewer, platform-admin] }
    - path: /apis/billing/**
      allow: { groups: [finance, platform-admin] }
    - path: /docs/internal/**
      allow: { groups: [finance, platform-admin] }
    - path: /apis/**
      allow: { groups: [platform-admin] }
```

| Tracking: read | 401 | 403 | ✅ | 403 | 403 | 403 | ✅ |
| Carriers: read / write | 401 | 403 | 403 | 403 | ✅ | 403 | ✅ |

| Admin: read / write | 401 | 403 | 403 | 403 | 403 | 403 | ✅ |

The **reviewer** row is the key case: reads most docs (section 5) but every call returns 403, even with Try enabled.

## 7. Scenarios to verify (step 6)

1. A visitor reads the public docs and calls the Rates API from Try; protected links show locks; opening one goes to sign-in.
2. ship@ reads and calls Shipments; Tracking shows "access denied".
3. track@ calls Tracking with OAuth; the API-key-only call also works with a key; Shipments is denied.
4. review@ reads Shipments, Tracking and Carriers; every Try call returns 403.
5. partner@ uploads a label (multipart) to Carriers; reads partner guides; no internal docs.
6. finance@ reads internal runbooks and Billing; the mock generates billing data from schemas.
7. manager@ reads and calls everything, including the large Admin API; search finds admin operations only for manager@.
8. Search for each user returns only what that user may read.
9. Sign out (`logout: idp`) and sign in as someone else without stale access.
